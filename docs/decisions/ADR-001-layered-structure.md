# ADR-001: 構造はレイヤード(最軽量)を採用する

層: decisions / 正本: この文書 / 版: 2026-08-16

<!-- devbase/templates/ADR.md v1(Nygard 形式)。docs/decisions/ の1件目。 -->

- **状態**: 採用
- **文脈**: A-2(devbase 標準適用)の基本設計工程で構造を選定する必要があった。
  `devbase/verification/structure-catalog.md` の既存プロジェクトへの当てはめ表は unit-converter を
  「レイヤード(最軽量)=単機能 CLI」と見立てていた。この見立てを実コード(`bin/conv.js`・
  `src/convert.js`・`src/units.js` の3ファイル)に照らして検証した。
- **決定**: **レイヤード(最軽量)** を採用する。根拠は実装の依存方向そのものにある。
  - `bin/conv.js`(入口層。引数解析・出力整形)は `src/convert.js`・`src/units.js` を import する
  - `src/convert.js`(変換ロジック層)は `src/units.js` を import する
  - `src/units.js`(データ層。単位換算係数とカテゴリ判定)は他のどのファイルも import しない
    (`grep -n "^import" bin/*.js src/*.js` で確認。逆方向の import はゼロ)
  - 入口→ロジック→データの**一方向の依存**のみで、循環・飛び越しは無い。3ファイル・単一責務の
    CLI にヘキサゴナルやモジュラーモノリスは過剰(catalog の「過剰になる」欄どおり)
- **捨てた案**:
  - パイプライン: 変換処理は「入力パース→単位解決→計算→整形」という段があるように見えるが、
    実装は `convert()` 一関数呼び出しで完結しており、段を跨ぐ独立ファイル(パイプラインの離散段)
    には分かれていない。レイヤードの「層」の方が実態(3ファイルの依存方向)に近い
  - ヘキサゴナル: 外部接続(API/DB/複数入出力)が無く、ポート&アダプタを置く動機が無い
  - モジュラーモノリス: 機能領域は「変換」の一つのみ。境界(公開面)を切るほどの規模ではない
- **帰結**: G8 検収(構造検収)は「`src/units.js` は他のどのファイルも import しない
  (データ層は最内層)」「`bin/conv.js` は他のどのファイルからも import されない(入口は終端)」を
  本来 `.dependency-cruiser.cjs` で検収する。**現状は未導入**(3ファイル規模のため憲章6節に
  「対象外+理由」として明記。目視・grep で足りる規模。ファイル数が増えたら導入する)。
